# Проектный промт: mygasproject

## Общая цель проекта

Проект предназначен для:
1. Импорта данных из XLSX-файла, который автоматически попадает в папку Google Drive.
2. Нормализации этих данных в лист `Info` Google Sheets по жёстко заданной схеме.
3. Построения расчётного ядра в листе `report`.
4. Построения аналитических дашбордов на основе `report`.
5. Автоматического обновления данных по триггерам через Apps Script.

---

## Главные архитектурные принципы

### 1. Ядро расчётов — только в `report`
Все расчётные показатели должны концентрироваться в ядре `report`.

Это правило обязательно для дальнейшей разработки.

В `report` должны жить:
- агрегаты по заказам
- производные показатели
- показатели остатков
- расчётные поля типа:
  - `ordersFBO`
  - `ordersFBS`
  - `orderssum`
  - `sumstock`
  - `dayorders`
  - `zapas`
- в будущем любые новые расчётные поля

### 2. Дашборды — только визуализация
Файлы дашбордов не должны содержать ядро расчётов.

Дашборды должны:
- читать готовые данные из `report`
- визуализировать
- фильтровать
- группировать
- форматировать

Если удалить файл конкретного дашборда из проекта:
- импорт
- report
- триггеры
не должны ломаться.

### 3. Каждый дашборд — отдельный файл
Структура по дашбордам:
- `dashboard1.gs`
- `dashboard2.gs`
- `dashboard3.gs`
и так далее

Каждый такой файл должен содержать только логику конкретного дашборда.

### 4. Триггеры не должны строить дашборды
Триггеры должны выполнять только:
- импорт
- построение `report`

Дашборды запускаются только вручную из `onOpen` / меню.

### 5. Схемы должны быть вынесены отдельно
Все схемы колонок и имена переменных хранятся централизованно в `Schema.gs`.

`Schema.gs` должен располагаться выше других файлов в Apps Script editor, потому что другие файлы используют его глобальные константы.

## Структура файлов проекта

### `Code.gs`
Главное меню проекта через `onOpen`.

В этом файле:
- создаётся меню
- запускаются ручные функции из UI
- никаких тяжёлых расчётов быть не должно

Типовые функции:
- `onOpen(e)`
- `runImportXlsxFromMenu()`
- `runBuildReportFromMenu()`
- `runRefreshAllFromMenu()`
- `runBuildDashboard1FromMenu()`
- `showDashboard1Html()` может также быть доступен из меню, если используется HTML-дашборд

### `Schema.gs`
Центральное место хранения схем.

Содержит:
- `INFO_SCHEMA`
- `INFO_COLUMNS`
- `INFO_HEADERS`
- `ORDERS_HEADERS`
- `ORDERS_COLUMNS`

### `ImportXlsx.gs`
Импорт XLSX в лист `Info`.

Содержит:
- конфиг импорта
- логику выбора XLSX
- логику импорта
- логику записи листа `Info`
- отдельную функцию для триггера

Важно:
- импорт использует `INFO_SCHEMA`
- заголовки `Info` жёстко задаются по схеме
- данные импортируются начиная со 2 строки XLSX
- 1 строка XLSX = заголовки
- сопоставление идёт по `sourceHeader`
- если колонки нет в XLSX, в `Info` пишется пустое значение

### `ImportXlsxDialog.html`
HTML-окно выбора XLSX-файла для ручного импорта.

Используется только как UI-обвязка для ручного запуска.

### `Report.gs`
Расчётное ядро проекта.

Содержит:
- чтение `Info`
- чтение `orders`
- связь `orders.nmid = info.artwb`
- все расчётные поля
- полную перезапись листа `report`

Важно:
- все будущие вычисления добавляются сюда
- дашборды не должны пересчитывать бизнес-логику повторно

### `Triggers.gs`
Только триггеры для:
- `import -> report`

Не должен зависеть от файлов дашбордов.

Типовые функции:
- `refreshAllDataForTrigger()`
- `createEvery15MinutesRefreshTrigger()`
- `createHourlyRefreshTrigger()`
- `createDailyRefreshTriggerAt9()`
- `createDailyRefreshTriggerAt12()`
- `createDailyRefreshTriggerAt18()`
- `logProjectTriggers()`
- `deleteAllProjectTriggers()`

### `dashboard1.gs`
Только построение листа `Dashboard1`.

Должен:
- читать `report`
- визуализировать данные
- добавлять форматирование
- добавлять фильтры / слайсеры / группировку
- не содержать ядра расчётов

### `dashboard1html.gs`
Серверная часть HTML-дашборда.

Должен:
- собирать данные для HTML-окна
- читать `report`
- при необходимости читать `orders`, если нужны визуальные ряды, но в перспективе лучше и это вынести в `report`

### `Dashboard1Window.html`
HTML-версия Dashboard1.

Должен:
- показывать KPI
- показывать фильтры
- строить визуальную таблицу
- показывать мини-графики
- быть отдельным интерфейсом, не влияющим на остальную архитектуру

### `schema.md`
Документация схемы проекта.

Содержит:
- актуальную `Info schema`
- актуальную `Orders schema`
- в будущем сюда можно добавить:
  - `Report schema`
  - `Dashboard schema`

## Лист `report`

### Назначение
Центральное расчётное ядро.

### Правила включения строки в `report`
Строка из `Info` попадает в `report` только если:
- `artwb` не пустой
- `artwb` не равен `0`

Условие по `tg1` использовать **не нужно**.

### Что переносится из `Info`
В `report` переносятся все поля из `Info`, у которых задан `varName`.

### Связь с `orders`
Связь:
- `orders.nmid = info.artwb`

### Расчёты по заказам
Используются только заказы, где:
- `iscancel = 0`

Поля:
- `ordersFBO` = count заказов по `nmid`, где `warehousetype = "Склад WB"`
- `ordersFBS` = count заказов по `nmid`, где `warehousetype = "Склад продавца"`
- `orderssum` = общее количество заказов по `nmid`

### Остатки
- `sumstock = stock + reserved + shipped + fbostock`

### Средняя скорость заказов
- `dayorders` рассчитывается по последним 14 дням
- используется не деление на 14 всегда, а:
  - `dayorders = total orders за 14 дней / количество дней, в которые были заказы`

### Запас
- `zapas = sumstock / dayorders`

Если `dayorders = 0` или пустой, `zapas` должен быть пустым.

### В будущем
Все новые расчётные поля добавлять только сюда.

Сейчас реализуется отдельно на дашборде.
Но стратегически лучше, чтобы и он со временем тоже рассчитывался в `report`.

- `brandinfo`
  - внутри `tg1`

      - внутри `tg3`

Колонки:
- `brandinfo`
- `tg1`
- `tg2`

можно хранить и использовать для фильтров, но можно скрывать в финальном виде.

Нужны фильтры по:

- `brandinfo`

## Импорт XLSX

### Правила
- XLSX берётся из указанной папки Google Drive
- есть ручной режим через HTML-диалог выбора файла
- есть отдельная функция для триггера:
  - выбирает самый свежий XLSX
  - импортирует без UI

### Конвертация
Используется временная конвертация XLSX в Google Sheets через Drive API.

Для этого нужен включённый:
- Advanced Drive Service

### Авторизация
Повторная регулярная авторизация для импорта обычно не нужна.
Нужно:
- один раз авторизовать скрипт
- один раз включить нужные сервисы
- потом использовать installable triggers

### Что не нужно делать
Не нужно переносить рабочий импорт данных в GitHub Actions.
GitHub Actions используется только для деплоя кода через `clasp`, а не для регулярного рабочего импорта.

## Правила по разработке новых функций

1. Если нужна новая аналитика — сначала добавлять её в `report`.
2. Дашборды должны читать готовые расчёты из `report`.
3. Новые дашборды делать только отдельными файлами.
4. Не дублировать глобальные `const` между файлами Apps Script.
5. Все общие схемы хранить только в `Schema.gs`.
6. Стараться избегать вычислений на верхнем уровне файлов, если они зависят от других глобальных объектов.
7. Если Apps Script падает с `Identifier has already been declared`, значит в другом файле уже есть такой глобальный `const`.
8. Если исчезает `onOpen`, сначала проверять синтаксические ошибки и дубли глобальных объявлений.

---

## Правила по Apps Script

1. Все `.gs` файлы живут в одном глобальном пространстве имён.
2. Поэтому нельзя повторно объявлять одинаковые глобальные `const`.
3. `Schema.gs` должен быть выше других файлов.
4. `onOpen` должен быть один.
5. Для UI-функций использовать:
   - меню
   - HTML-dialog
6. Для триггеров использовать только функции без UI.
7. Для Sheets API особенностей учитывать, что не все методы Spreadsheet service существуют так, как ожидается.
